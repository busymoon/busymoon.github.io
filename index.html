Redis 三大经典场景：分布式锁 / 秒杀扣减 / 实时排行榜

你的核心直觉完全正确——这三个场景之所以都用 Redis，本质上都是在利用它的单线程内存原子性（在数据原地完成判断与修改，避免多线程并发覆盖）。

如果把这段理解放到资深架构师面试的语境下，你只需要在每个场景里做一次”精准指令校准”，再补上**”高并发下的一个致命坑点”**，回答就会非常专业：

1. 分布式锁：不是 INCR，而是 SET NX PX + Lua 解锁

  • 精准指令：加锁用的是 SET lock_key unique_id NX PX 30000（NX 保证不存在才写入，PX 设置自动过期防死锁，unique_id 标识锁的持有者）。
  • 架构师必提的两个坑：
  1. 防误删（解锁原子性）：业务执行完释放锁时，不能直接 DEL，必须用 Lua 脚本先判断 value == unique_id 再删除（防止 A 线程超时锁自动过期后，误删了 B 线程刚抢到的锁）。
  2. 主从切换丢锁（CAP 权衡）：因为 Redis 主从是异步复制的，如果 Master 刚加完锁还没同步给 Slave 就宕机了，Slave 升主后会导致第二个客户端也能抢到锁。因此强资金安全场景不能用 Redis 锁（要用 etcd/ZooKeeper），Redis 锁只适合防重放、防并发抖动等允许极小概率冲突的场景。

2. 秒杀库存扣减：不能单纯 DECR，必须用 Lua 原子校验 + 库存分桶

  • 精准指令：如果先 GET 判断库存 > 0 再 DECR，高并发下依然会超卖（两条请求同时读到库存为 1）。生产环境必须用 Lua 脚本把”判断 库存 >= 购买数量“和”扣减库存”打包成一个原子操作；或者直接用 DECR 扣减后判断返回值是否 < 0（小于 0 则回滚并提示售罄）。
  • 架构师必提的坑（Hot Key 单点瓶颈）：
  • 哪怕用 Lua 保证了不超卖，如果 50 万人同时秒杀同一款 iPhone，所有请求都会砸向同一个商品 Key 所在的单台 Redis 节点。
  • 高阶解法（库存分桶）：把 1,000 件库存拆成 10 个子 Key（如 stock_item_1 到 stock_item_10，每个 100 件），请求进来按用户 ID 哈希路由到不同分片并发扣减，吞吐直接翻 10 倍。

3. 实时排行榜：底层是 ZSet，高频点击需先”端侧攒批”

  • 精准指令：排行榜依靠的是 ZSet（有序集合，底层由跳表 + 哈希表实现）。每次点击或展现调用 ZINCRBY 累加分值，查询前 100 名调用 ZREVRANGE，复杂度仅为 $O(\log N)$。
  • 架构师必提的坑（写放大与热 Key）：
  • 如果是大型信息流或直播间，每秒有几十万次”展现/点赞”，每次都直连 Redis 执行 ZINCRBY 会打满网络和单分片 CPU。
  • 高阶解法（内存聚合攒批）：在业务服务器本地内存里开一个滑动窗口，把同一个对象 200ms 内的 500 次点击先合并成一个 +500 的增量，再批量刷入 Redis，写压力直接降低两个数量级。

一句话串联这三者的本质：

分布式锁靠 SET NX 占坑，秒杀靠 Lua 脚本原子判减，排行榜靠 ZSet 原地累加——三者共性都是用单线程消除锁竞争，但一旦并发量级上来，都必须防范单个 Key 变成热点。

什么是 Count-Min Sketch？

什么是 Count-Min Sketch？

Count-Min Sketch（CMS，计数最小草图）是一种用于统计数据流中元素出现次数的概率性数据结构。

它的核心思想是：

不保存每个元素的真实计数，而是使用一个固定大小的二维数组，通过多个哈希函数记录计数，从而用很少的内存估算任意元素出现的次数。

它特别适合处理海量数据，例如：

  • 统计 Telegram 中每个关键词出现的次数
  • 统计网站中每个 URL 被访问的次数
  • 统计日志中每种错误出现的频率
  • 统计数据流中的热门用户、热门商品

一、为什么需要 Count-Min Sketch？

假设我们需要统计 10 亿条数据中，每个关键词出现的次数。

最直接的方法是使用 HashMap：

这种方法可以准确统计，但存在一个问题：

如果关键词有 1 亿种，就需要保存 1 亿个键值对。

对于内存有限、数据持续流入的系统，这种方式可能成本很高。

Count-Min Sketch 的目标是：

牺牲少量计数精度，换取极低的内存占用。

二、Count-Min Sketch 的核心结构

它使用一个二维计数矩阵。

  • 4 个哈希函数

4 个哈希函数 × 每行 10 个计数器

每一行对应一个独立的哈希函数，每一列是一个计数器。

1. 插入一个元素

假设我们插入关键词 apple。

4 个哈希函数分别计算：

哈希函数 计算结果
h₁(apple) 2
h₂(apple) 5
h₃(apple) 1
h₄(apple) 7

于是，将这 4 个位置的计数器分别加 1。

如果再插入一次 apple，这 4 个计数器再分别加 1。

2. 查询一个元素

查询 apple 时，重新计算这 4 个哈希位置，读取对应的计数器。

假设读取结果为：

哈希函数 计数器值
h₁(apple) 12
h₂(apple) 15
h₃(apple) 12
h₄(apple) 18

那么 CMS 返回：

\[ \hat f(\text{apple})=\min(12,15,12,18)=12 \]

也就是返回最小值 12，作为 apple 出现次数的估计。

为什么取最小值？因为哈希冲突只会让计数器增加，不会减少。

因此，CMS 的估计值通常是真实频率的上界。

三、为什么取最小值能够降低误差？

假设 apple 实际出现了 10 次。

但是其他关键词也可能被哈希到相同的位置，导致计数器被额外增加。

例如：

  • 第 1 行计数器：12
  • 第 2 行计数器：15
  • 第 3 行计数器：10
  • 第 4 行计数器：13

其中第 3 行恰好没有受到其他关键词的冲突影响。

取最小值：

\[ \min(12,15,10,13)=10 \]

就得到了真实频率。

当然，如果所有行都发生了冲突，最小值也会高于真实频率。

这就是 CMS 的主要误差来源：哈希碰撞导致计数被高估。

四、Count-Min Sketch 的误差保证

CMS 不只是一个经验性的近似算法，它具有明确的概率误差保证。

设：

  • \(N\)：整个数据流中元素的总数量
  • \(\epsilon\)：允许的相对误差参数
  • \(\delta\)：允许出现误差超标的概率

CMS 可以通过设置矩阵宽度和深度，保证：

\[ \hat f(x)\leq f(x)+\epsilon N \]

并且：

\[ P\left(\hat f(x)>f(x)+\epsilon N\right)\leq\delta \]

常见的参数设置为：

\[ w=\left\lceil\frac{e}{\epsilon}\right\rceil \]

\[ d=\left\lceil\ln\frac{1}{\delta}\right\rceil \]

其中：

  • \(w\)：矩阵宽度
  • \(d\)：矩阵深度

矩阵需要的计数器数量约为：

\[ w\times d \]

例如，允许误差参数 \(\epsilon=0.001\)，失败概率 \(\delta=0.01\)，则大约需要：

  • 宽度：2719
  • 深度：5
  • 总计：约 13,595 个计数器

如果每个计数器使用 4 字节整数，内存仅约 53 KB。

这就可以统计非常大的数据流，而不需要保存所有元素。

五、Count-Min Sketch 的优缺点

优点 缺点
内存占用固定 计数可能被高估
适合处理无限数据流 不能准确恢复所有元素
插入和查询速度快 不适合删除元素
可以合并多个 Sketch 无法直接列出所有热门元素

需要注意：CMS 本身只能回答”某个元素大约出现了多少次”，不能直接回答”出现次数最多的 100 个元素是谁”。

如果需要统计 Top-K，通常会将 CMS 与 Heap、Space-Saving 等结构组合使用。

六、与 HashMap 的区别

对比 HashMap Count-Min Sketch
计数准确性 精确 近似
内存 随元素种类增长 固定
查询复杂度 平均 O(1) O(d)
插入复杂度 平均 O(1) O(d)
是否保存元素名称 是 否

最重要的理解：

HashMap 是为每个元素单独保存一个计数器。

Count-Min Sketch 则是让所有元素共享一组计数器，通过哈希映射把元素的计数分散到矩阵中。

它用空间换取了统计能力的扩展性，同时通过多个哈希函数和取最小值来控制误差。

这也是它在大规模数据流处理、网络流量分析、搜索引擎和实时监控系统中非常有价值的原因。

Day4 - 学习总结

今日 Agent 学习要点

Q1：什么是 Skill？
A：Agent 中一项可复用的能力，类似软件工程中的 Service / Capability。

Q2：什么是 Prompt？
A：指导 LLM 执行某个认知动作的 Instructions，是 Skill 的组成部分之一。

Q3：Skill 和 Prompt 的关系是什么？
A：Skill ≠ Prompt。一个 Skill 可以包含 Prompt、Context、Taxonomy、Policy、Few-shot、Tool、Output Schema、Eval 等，也可以包含多次 LLM 调用。

Q4：Workflow 和 Skill 的关系是什么？
A：Workflow 负责组织多个 Skill/Tool 完成整体目标；Skill 负责提供具体能力。

Q5：Prompt、Context 的区别是什么？
A：Prompt 决定“怎么做”；Context 决定“这一次做的时候知道什么”。

Q6：Taxonomy 是什么？
A：定义系统中“有哪些概念/答案”。

Q7：Decision Policy 是什么？
A：定义如何根据证据从多个候选答案中做出判断。

Q8：Few-shot 是什么？
A：通过具体案例向模型示范如何应用抽象的 Policy。

Q9：Tool 是什么？
A：Agent 用于获取信息、执行计算、验证结果或改变外部环境的确定性能力。

Q10：什么时候应该用 Tool，而不是 LLM？
A：能够通过确定性计算、查询、验证或转换得到的结果，优先交给 Tool。

Q11：Eval 是什么？
A：衡量 Skill/Agent 是否正确，以及修改后是否真正改善、是否产生 Regression。

Q12：Agent 的核心运行循环是什么？
A：Observe → Decide → Act → Observe，直到 Goal 完成或终止。

Q13：Observe 是什么？
A：Agent 获取当前环境、任务和工具执行结果等信息。

Q14：Decide 是什么？
A：根据 Goal、State、Context、Policy 和 Available Actions 决定下一步行动。

Q15：Act 是什么？
A：调用 Tool、Skill、Human 等执行 Decision，产生新的 Observation。

Q16：为什么同一个错误结果可能有不同原因？
A：可能是 Observe 信息缺失、Decide 判断错误，也可能是 Act 执行错误，需要 Failure Decomposition。

Q17：什么是 State？
A：描述当前任务“现在做到哪里、处于什么状态”。

Q18：什么是 Context？
A：为了当前这一次 Decision，选择让模型看到的信息。

Q19：什么是 Memory？
A：从过去经历中保留下来、未来任务可能再次使用的信息。

Q20：什么是 History？
A：记录过去发生过什么；History 是“怎么走到这里”，State 是“现在在哪里”。

Q21：Memory 和 Knowledge 有什么区别？
A：Memory 主要来自历史运行和交互经验；Knowledge 是相对稳定、权威、经过治理的外部知识。

Q22：Memory 是否一定要变成 Knowledge？
A：不一定。只有经过审核、治理后，部分 Memory 才可能沉淀为正式 Knowledge。

Q23：Memory 如何影响未来 Decision？
A：Memory → Retrieval → Context → LLM → Decision。

Q24：Memory 系统最核心的两个问题是什么？
A：什么时候记（Memory Write Policy）和什么时候想起来（Memory Retrieval Policy）。

Q25：State、Context、Memory 最简单的记忆方式是什么？
A：State = Where am I?；Context = What do I need to know now?；Memory = What from the past should I remember?

Q26：Context 的信息可以来自哪里？
A：State、Observation、History、Memory、Knowledge、Tool Results、用户输入等。

Q27：Context Engineering 的核心是什么？
A：为当前 Goal + State + Decision 选择最合适的信息，而不是简单把所有信息塞给 LLM。

Q28：Agent 架构设计中的重要原则是什么？
A：结果错误时不要默认“改 Prompt”，先定位错误属于 Prompt、Context、Taxonomy、Policy、Few-shot、Tool、Workflow、State/Memory 还是其他层。
