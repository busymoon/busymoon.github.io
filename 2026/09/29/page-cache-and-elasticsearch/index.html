从 Page Cache 到 Elasticsearch：操作系统缓存与近实时写入的本质

这两篇文档其实是在讲同一件事的两个面：操作系统内核用 Page Cache 缓存一切文件读写，而 Elasticsearch 的”近实时”能力，本质上就是借力 Page Cache 换来的。合并成一篇，你就能把底层缓存机制和应用层架构串起来。

第一篇：Page Cache 内核篇

内核不需要提前”猜”哪些数据热门，它的规则极其简单粗暴：默认情况下，只要应用程序通过标准文件系统接口读写硬盘文件，就必须经过 Page Cache（凡走必留痕）。

具体来说，内核通过以下 3 种机制把数据装进 Page Cache，同时留了 1 个旁路后门：

一、数据是怎么被放进 Page Cache 的？（3 条路径）

1. 读文件时”顺手留下”（Read Cache）

  • 当程序调用 read() 读取文件某一段数据时，内核先查 Page Cache（以 文件描述符 + 文件内偏移量 为索引，每页 4KB）。
  • 如果没命中：内核去硬盘把这 4KB 读进 Page Cache，再拷贝一份给应用程序。这样下次再读同一块数据时，直接从内存秒出。

2. 写文件时”先记账、后落盘”（Write-Back 写回机制）

  • 当程序调用 write() 写文件时（比如 ES 写 Translog、Kafka 追加消息），内核根本不直接写硬盘，而是把数据直接塞进 Page Cache，把这几页标记为”脏页（Dirty Page）”，然后立刻告诉程序”写入成功”。
  • 随后，内核后台的刷盘线程（flusher）会在脏页比例超标或超时（默认 30 秒）时，默默把脏页批量刷进物理硬盘。

3. 顺序读时”提前预读”（Read-Ahead 顺藤摸瓜）

  • 内核非常聪明：如果它发现程序连续读取了文件的第 1 页、第 2 页、第 3 页，就会判定你在做顺序扫描（比如 StarRocks 扫列存文件、Kafka 顺序消费）。
  • 内核会主动在后台提前把第 4~32 页从硬盘预读进 Page Cache。等程序真正请求第 4 页时，数据早就躺在内存里等它了。

二、唯一的例外：什么时候不放进 Page Cache？

有些重型数据库（比如 MySQL InnoDB）自己写了一套极其精密的内存缓冲池（Buffer Pool），不希望操作系统插手管理缓存（否则同一份数据既在 InnoDB 内存里、又在 Page Cache 里，造成双倍内存浪费）。

  • 这类程序在打开文件时会显式加上 O_DIRECT（直接 I/O） 标志。
  • 加了这个标志后，读写请求会彻底绕开 Page Cache，直接在应用程序内存和物理硬盘之间传输数据。

三、放满了怎么办？（双链表 LRU 淘汰）

Page Cache 既然是动态蓄水池，内存紧张时内核会按改进版的 LRU（最近最少使用）算法清理：

  1. 干净页（已落盘）：直接丢弃，0 毫秒腾出内存。
  2. 脏页（未落盘）：必须先触发刷盘写进硬盘变成干净页，然后才能回收。

第二篇：Elasticsearch 写入篇

Elasticsearch 的写入与查询机制，核心是在解决同一个矛盾：底层 Lucene 的倒排索引文件（Segment）一旦生成就不可修改（Immutable）。

围绕这个物理铁律，ES 设计了 “借力 OS 缓存实现秒级可搜” 的写入流水线，但也埋下了 “合并开销大” 和 “分布式深分页爆炸” 两个经典深坑。

一、近实时写入三步曲：Refresh / Flush / Merge

一次数据写入 ES，不会立刻刷进物理硬盘（太慢），而是走完下面 3 个阶段：

1. Refresh（默认 1 秒一次 ➔ 数据”可被搜索”）

  • 动作：新写入的文档先进入 JVM Memory Buffer（此时搜不到），同时顺序追加写入 Translog（事务日志，防断电丢数据）。每隔 1 秒，ES 执行一次 Refresh：把内存 Buffer 里的数据生成一个新的倒排索引小文件（Segment），并写进操作系统的 Page Cache（内存页缓存）。
  • 架构精髓：只要进了 OS Page Cache，文件就可以像磁盘文件一样被读取搜索，但省去了物理落盘的耗时。这就是为什么 ES 叫 “近实时（NRT，延迟 1 秒）”。

2. Flush（默认 30 分钟或 Translog 满 512MB ➔ 数据”真正落盘”）

  • 动作：调用操作系统的 fsync，把 Page Cache 里的所有 Segment 强制刷进物理硬盘，写入提交点（Commit Point），然后清空旧的 Translog。
  • 架构精髓：用周期性的批量刷盘替代每次写入刷盘，大幅压低磁盘 I/O。

3. Segment Merge（后台持续进行 ➔ 合并碎文件 + 物理删除）

  • 动作：每 1 秒 Refresh 就会产生一个新 Segment，一天下来会有几万个碎文件，严重拖慢查询。后台线程会自动把多个小 Segment 合并成一个大 Segment，并在此过程中真正物理清理掉被标记为 deleted 的旧文档。
  • 日志写入优化铁律：
  1. 调大 refresh_interval：日志与异常分析场景不需要 1 秒可搜，改成 30s 或 60s，生成 Segment 的频率直接降低 30 倍，写入吞吐翻倍。
  2. 禁止高频更新（Update）：因为 Segment 不可变，ES 的更新本质是 “旧文档打删除标 + 写入一条全新文档”，高频更新会引发极其惨烈的磁盘 Merge 风暴（这类场景应直接选 StarRocks 主键模型）。

二、深分页灾难（from + size）与三大解法

1. 为什么 from=100000, size=10 会直接打挂 ES 节点？

ES 是分散汇总（Scatter-Gather）架构，假设你的索引有 5 个分片（Shard）：

  • 当你请求第 100,000 到 100,010 条数据时，协调节点根本不知道全局第 10 万条落在哪个分片上。
  • 它只能命令每一个分片都在本地排序并取出 前 100,010 条（共 5 × 100,010 = 500,050 条完整文档）全部传回协调节点。
  • 协调节点在 JVM 堆内存里对这 50 万条数据做全局归并排序，最后只取 10 条返回，把其余 499,990 条全部扔掉。页码越深，内存和网络呈指数级放大，直接触发协调节点 OOM。

2. 生产环境的三种标准解法

解法 核心原理 适用场景与代价
1. search_after（生产绝对主力） 游标翻页：拿着上一页最后一条数据的排序字段值（如 [timestamp, _id]），作为下一页的过滤条件（WHERE time < last_time）。每个分片只需返回固定的 10 条，彻底消除内存膨胀。 适用：App 瀑布流下滑、”下一页”按钮。
代价：只能顺序向后翻，不支持跳页（如直接点第 50 页）。
2. PIT (Point In Time) + search_after 固定数据视图：翻页前先创建一个轻量级时间点快照（PIT），保证用户在连续翻页过程中，不会因为新数据不断写入而出现分页数据重复或漏掉。 适用：高并发写入下的稳定深度遍历，或后台异步全量导出（替代已废弃的旧版 Scroll API）。
3. 业务层限流（产品止血） 截断最大页码：保持 ES 默认限制 index.max_result_window = 10000（如每页 20 条，最多只允许看前 500 页）。 适用：面向人工排查的搜索框（类似百度/淘宝限制最大页数），引导用户通过缩小时间范围或补充关键词精准过滤。

串起来看

一句话总结（内核篇）

只要不加 O_DIRECT，内核对所有文件读写都执行”读时缓存、写时先暂存脏页、顺序读提前预读”；至于哪些该留、哪些该踢，全靠 LRU 淘汰算法让真正的热点文件自然沉淀在内存里。

一句话总结（ES 篇）

ES 写入靠 1 秒 Refresh 进 Page Cache 换近实时、靠 后台 Merge 清理碎片（日志场景务必调大 Refresh 间隔）；查询靠 search_after 游标 替代 from + size，彻底斩断分布式深分页的内存放大。

两者的本质联系

ES 的”近实时”就是 Page Cache 的写回机制：写入先进内存页缓存换秒级可搜，再靠周期性的 fsync（Flush）批量落盘——这正是在第一篇里说的”先记账、后落盘”。理解了内核的 Page Cache，你就看穿了 ES 整个写入流水线的设计动机。
