Redis 三大经典场景：分布式锁 / 秒杀扣减 / 实时排行榜

你的核心直觉完全正确——这三个场景之所以都用 Redis，本质上都是在利用它的单线程内存原子性（在数据原地完成判断与修改，避免多线程并发覆盖）。

如果把这段理解放到资深架构师面试的语境下，你只需要在每个场景里做一次”精准指令校准”，再补上**”高并发下的一个致命坑点”**，回答就会非常专业：

1. 分布式锁：不是 INCR，而是 SET NX PX + Lua 解锁

  • 精准指令：加锁用的是 SET lock_key unique_id NX PX 30000（NX 保证不存在才写入，PX 设置自动过期防死锁，unique_id 标识锁的持有者）。
  • 架构师必提的两个坑：
  1. 防误删（解锁原子性）：业务执行完释放锁时，不能直接 DEL，必须用 Lua 脚本先判断 value == unique_id 再删除（防止 A 线程超时锁自动过期后，误删了 B 线程刚抢到的锁）。
  2. 主从切换丢锁（CAP 权衡）：因为 Redis 主从是异步复制的，如果 Master 刚加完锁还没同步给 Slave 就宕机了，Slave 升主后会导致第二个客户端也能抢到锁。因此强资金安全场景不能用 Redis 锁（要用 etcd/ZooKeeper），Redis 锁只适合防重放、防并发抖动等允许极小概率冲突的场景。

2. 秒杀库存扣减：不能单纯 DECR，必须用 Lua 原子校验 + 库存分桶

  • 精准指令：如果先 GET 判断库存 > 0 再 DECR，高并发下依然会超卖（两条请求同时读到库存为 1）。生产环境必须用 Lua 脚本把”判断 库存 >= 购买数量“和”扣减库存”打包成一个原子操作；或者直接用 DECR 扣减后判断返回值是否 < 0（小于 0 则回滚并提示售罄）。
  • 架构师必提的坑（Hot Key 单点瓶颈）：
  • 哪怕用 Lua 保证了不超卖，如果 50 万人同时秒杀同一款 iPhone，所有请求都会砸向同一个商品 Key 所在的单台 Redis 节点。
  • 高阶解法（库存分桶）：把 1,000 件库存拆成 10 个子 Key（如 stock_item_1 到 stock_item_10，每个 100 件），请求进来按用户 ID 哈希路由到不同分片并发扣减，吞吐直接翻 10 倍。

3. 实时排行榜：底层是 ZSet，高频点击需先”端侧攒批”

  • 精准指令：排行榜依靠的是 ZSet（有序集合，底层由跳表 + 哈希表实现）。每次点击或展现调用 ZINCRBY 累加分值，查询前 100 名调用 ZREVRANGE，复杂度仅为 $O(\log N)$。
  • 架构师必提的坑（写放大与热 Key）：
  • 如果是大型信息流或直播间，每秒有几十万次”展现/点赞”，每次都直连 Redis 执行 ZINCRBY 会打满网络和单分片 CPU。
  • 高阶解法（内存聚合攒批）：在业务服务器本地内存里开一个滑动窗口，把同一个对象 200ms 内的 500 次点击先合并成一个 +500 的增量，再批量刷入 Redis，写压力直接降低两个数量级。

一句话串联这三者的本质：

分布式锁靠 SET NX 占坑，秒杀靠 Lua 脚本原子判减，排行榜靠 ZSet 原地累加——三者共性都是用单线程消除锁竞争，但一旦并发量级上来，都必须防范单个 Key 变成热点。
